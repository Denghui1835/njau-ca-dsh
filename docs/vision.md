# 愿景

> 这份文件回答一个问题：**为什么是这套东西，而不是一个官网？**
> 换届时先读这一份。它决定了后面所有技术选择。

---

## 一、起点：不做官网

最开始的念头是"给计协做个网站"。想清楚之后否掉了。

**官网的四个死法：**

1. **做完就定型。** 需求一变就得重做，而重做要人、要时间、要有人愿意干。
2. **只能"看"，不能"干活"。** 协会真正的痛点是事务 —— 纳新的表格、活动的立项书、
   年审的材料、报销的单据。官网对这些一件都帮不上。
3. **换届即烂尾。** 网站是"一个人的作品"，作者毕业就走了。下一届不敢改、不会改、
   改坏了没人修，最后变成一个打不开的地址。
4. **容易变成门面工程。** 花大力气做了个漂亮的首页，一年访问量两位数。

**协会缺的不是门面，是工具。**

## 二、转向：协会操作系统

DSH 的立场是「**一切皆插件**」—— 一个内核，能力全部以插件形式组合。

我们顺着这个立场，把协会的事务拆成一批插件。这个选择的直接好处：

- **每块能力独立。** 想加"纳新"，装 `recruit`；不想要了，摘掉。
  不会因为某个域出问题，整个系统瘫掉。
- **每年可以只改一小块。** 下一届不需要理解全部代码，只要接手自己关心的那个域。
- **深度优先。** 因为每块很窄，所以可以做得**很符合计协真实的业务流**，
  而不是做成一个"啥都会一点但啥都不精"的通用工具。

> 用户原话：「现在通用模型的感觉就是啥都会一点但啥都不精，要更符合计协的业务流。」
> 这句话是本项目的**验收标准**。

它同时**取代官网的位置** —— 不是做一个新官网，而是让"官网"这个概念变得不必要。
协会需要的页面（介绍、活动、资源），由 `site` 域在这套系统里生成，数据来自同一份台账。

## 三、七条设计公理

这七条是判断"某个功能该不该做、该怎么做"的依据。

### 公理 1：能干活 > 能看

一个功能如果只是"展示信息"，优先级最低。
一个功能如果"替人做了重复劳动"，优先级最高。

**推论**：年审材料自动填充 > 活动申请表单填充 > 活动风采展示页。

### 公理 2：数据是资产，代码是耗材

代码会被下一代重写，数据不会。所以数据格式要比代码活得久。

**推论**：数据一律 Markdown / YAML / JSON 纯文本，**永不引入数据库**。
       这样能进 git、能 diff、能回滚、能被十年后的人用记事本打开。

### 公理 3：深度优先于广度

宁可把"纳新"做成本校最顺的纳新工具，也不要做十个半成品。

**推论**：每个域插件必须写清楚计协**真实**的流程、字段、材料要求，
       而不是一个泛化的"活动管理"模板。

### 公理 4：交接是一等公民

每个功能在设计的这一刻就要回答："下一届怎么接手？"

**推论**：每个包必须有 `OWNER.md`；每个域必须有 `SKILL.md` 讲清楚流程；
       数据目录必须有可读的目录结构。

### 公理 5：红线内建，不是事后检查

合规不能靠"记得别犯"。要靠代码结构让它犯不了。

**推论**：`compliance` 域独立存在；技能文本里直接写明红线；
       涉及学校系统的操作**只做本地草稿**，把"提交"这一步永远留给人。

### 公理 6：可拆卸

任何一个插件被删掉，其余部分必须照常工作。

**推论**：插件之间**不互相调用**。跨域协作由**人（和 agent）编排多个插件的工具**完成。
       `core` 不提供任何 Cordis 服务给别的插件用。

### 公理 7：低维护

这套东西必须能在"没人管"的情况下活过一个学期。

**推论**：零运行时依赖；不 fork DSH 的界面；不自己造服务器。
       能用 DSH 现成机制实现的，绝不自己写一套。

## 五、四个被明确点名的方向

### 1. `school` —— 年审材料 + 社团管理系统

**为什么最重要**：这是每年最痛苦、最重复、最容易出错的事。

- **年审材料**：学校有固定模板与固定字段（社团基本信息、负责人、成员数、
  活动清单、财务情况、工作总结……）。这些数据我们**本来就有**，
  散在 `events` / `finance` / `report` 各个域的台账里。
  → 做成"一键从台账生成年审材料草稿"，人工只做核对。

- **活动申请表单**：社团管理系统里的活动申请要填一堆字段（时间、地点、
  人数、经费、安全预案……），录入过程枯燥且容易填错。
  → 做成"本地填好 → 生成待粘贴文本 → 人工贴进系统"。

> ⚠️ **硬红线**：**绝不**对这个系统做自动登录、接口抓取或模拟点击。
> 理由有三：技术上脆弱（页面一改就废）、合规上有风险（一票否决项）、
> 道义上不该。系统的边界就是"帮人把字准备好"。

### 2. `library` —— 共享资源库

部署在**学校服务器**上，用来放学习资料与共享资源。

- 本地维护一份**资源索引**（纯文本，进 git），描述每个资源的标题、路径、
  适用人群、来源、授权状态。
- 服务器上放实际文件；索引与文件通过约定好的路径规则对应。
- **授权状态是必填字段** —— 不清楚来源的资料不许入库。

### 3. `deck` —— PPT 生成与修改

目标是**替代 WPS** 这条日常需求。

- 生成：从大纲/台账生成 PPT（纳新宣讲、活动总结、竞赛答辩）。
- 修改：读取现有 PPT，改文字、换图、调页序。
- 模板：把协会常用的几套版式固化成模板，避免每次从零排版。

> 实现上复用 DSH 自带的 Office 能力（`office-pptx`），
> 不自己造解析器 —— 见公理 7。

### 4. `workflow` —— 工作流骨架

**要解决的问题**：DSH 一跑就停不下来，或者跑偏了没人拦。

做法是给"跑一次任务"套上固定骨架：

| 机制 | 作用 |
| --- | --- |
| **DoD（完成定义）** | 开工前先写清楚"什么叫做完了"，避免无限打磨 |
| **预算** | 限定轮数/时间/工具调用次数，超了就停 |
| **分段退出** | 把大任务切成段，每段结束必须汇报，而不是一口气跑到底 |
| **检查点** | 中途把状态落盘，跑飞了能从检查点恢复 |
| **只读优先** | 默认先只读探查，确认清楚了再动写操作 |

## 六、成长五线

`growth` 域服务同学个人的五条路线 —— 这是"更符合我们学生的生态"。

| 路线 | 内容 |
| --- | --- |
| **创业** | 项目点子、团队组建、竞赛转化、校内科创资源 |
| **就业** | 简历、面试、实习信息、岗位方向、学长去向 |
| **科研** | 进实验室、读论文、做课题、找导师 |
| **升学** | 保研/考研信息、时间线、院校与方向选择 |
| **学习** | 课程、技术路线、刷题、项目练手 |

**设计原则**：每条路线都要有**具体的时间线**（什么时候该做什么），
而不是一堆链接。因为"什么时候做什么"才是学生真正会问的问题。

## 七、品牌与人设

品牌 = **人设 + 界面**，两件事。

- **人设**：系统说话像个懂行的学长学姐，不是通用助手。
  落在 `packages/brand/lib/index.js` 的 `PERSONA` 常量里。
- **界面**：
  - 侧栏标识与名称 —— 用 `priority: -1` 占住 `sidebar.brand.mark` /
    `sidebar.brand.name` 两个 slot，盖过官方图标。
  - 窗口标题与主色 —— 通过 `webserver/index-inject` 注入。
  - 主题色 —— 覆盖 token `--dsw-alias-brand-primary`。

> **关键认识**：DSH **没有品牌配置面**。品牌不是"设置"出来的，
> 是**占 slot 占出来的**。这是本项目的核心技术发现之一，
> 详见 `docs/architecture.md`。

**品牌红线**：不画校徽、不写学校全称、不用学校标准色。
协会是学生社团，**不是学校官方**，视觉上必须能区分开。

## 八、合规

协会处于**限期整改**期间。合规不是"注意一下"，是**一票否决**。

必须内建到设计里：

- ❌ 社团不能作为商业签约/收款主体 → 不做任何合同、收款、开票功能。
- ❌ 不冒充学校官方 → 品牌视觉与文案严格区分。
- ❌ 关联方回避 → 涉及经费的功能必须有回避提示。
- ❌ 新媒体账号超量/未报备/僵尸号 → `compliance` 域逐条检查。
- ❌ 线上舆情 → 对外文案发布前必须过审。
- ❌ **绝不**自动化操作学校系统。

> **整改期间不做无关工作。** 这条优先级高于本仓库的任何功能开发。

## 九、"传下去"的机制

这是本项目区别于"又一个学生项目"的地方。

| 机制 | 说明 |
| --- | --- |
| **`OWNER.md`** | 每个包都有，写明谁负责、交接要交代什么 |
| **`SKILL.md`** | 每个域都有，把**流程**写进系统，而不是写进某个人的脑子 |
| **`docs/adr/`** | 重要决定记录"为什么"，避免下届推翻时不知道代价 |
| **`HANDOVER.md`** | 换届清单，照着打勾即可 |
| **学年归档** | `docs/archive/<学年>/` + git tag `v<学年>`，形成证据链 |
| **纯文本数据** | 十年后仍能用记事本打开 |

**判定标准**（用户原话）：

> 「下一届的人能不能在**不问你任何问题**的情况下，把一次纳新完整跑一遍。」

这句话就是本项目的最终验收标准。**文档写得再全，跑不通就是没做完。**

**顺序理由**：先把"防跑飞"和"红线"做掉（P2），
再打通一条**完整的纳新闭环**（P3）—— 因为验收标准就是纳新。
之后才有意义地扩展。

## 十一、非目标（明确不做）

写下来是为了**以后不被带偏**。

- ❌ **不做官网那种门面。** 不做"首页大图 + 活动风采"。
- ❌ **不 fork DSH 界面。** 升级会废，维护不起。
- ❌ **不引入数据库。** 违反公理 2。
- ❌ **不做通用工具。** 违反公理 3。
- ❌ **不做机房设备运维。** 明确排除。
- ❌ **不做任何自动化操作学校系统的功能。** 违反红线。
- ❌ **不做商业签约/收款/开票。** 违反红线。
- ❌ **不把内部敏感材料写进仓库。** 违反红线。
- ❌ **不自建服务器/反向代理**（除非协会确有对外发布需求，且按学校规定办）。

## 十二、一句话总结

> 我们不是给协会做了个网站，
> 而是给协会做了一套**会随着每一届人成长、并且能被下一届完整接手**的工具。
>
> 它深度贴合计协真实的业务流，红线内建，数据是资产，代码是耗材。
