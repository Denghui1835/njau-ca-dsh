# 计协 DSH 生态 · 架构蓝图 v0.2

> 南京农业大学计算机爱好者协会（NJAU Computer Enthusiasts Association）
> 目标：**一个 DSH，处理计协的大大小小的事。一切皆插件。**

---

## 一、为什么不是「做个网站」

网站是「一个入口 + 一堆页面」，它的问题在于：

- 内容是**死**的——写完就烂在那，没人维护；
- 事务是**散**的——纳新在问卷星、报销在 Excel、周报在微信群、活动在腾讯文档；
- 交接是**断**的——上届的东西下届找不到，找到了也看不懂为什么这么做。

而 DSH 提供的是**一个能干活的 Agent 运行时 + 一套插件装载机制**。所以正确的形态不是「给协会做个网站」，而是：

> **把协会的每一件事，做成一个插件，装进同一个 DSH。**

于是「计协的事务」和「计协的 AI」是同一件事：你说一句「把上周的例会纪要整理成周报，顺便把新人的报名表汇总一下」，DSH 就真的去干了——因为它手上有 `report` 插件和 `recruit` 插件。

## 二、设计公理

| 公理 | 含义 | 后果 |
|---|---|---|
| **一切皆插件** | 每个业务域 = 一个独立 npm 包 = 一个 Cordis 插件 | 任一域可以单独升级、单独废弃、单独交给某一届的某人 |
| **内核极薄** | `core` 只提供身份、术语、共享数据层，不含任何业务 | core 稳定 = 生态稳定 |
| **插件之间不直连** | 域插件只依赖 `core`，彼此通过 core 的数据层或事件通信 | 删掉任一业务插件，其余照常启动 |
| **数据在文件里** | 协会数据是仓库里的 Markdown/YAML/JSON，不是数据库 | git 可 diff、可回滚、可交接；明年的人看得懂 |
| **知识即技能** | 制度、SOP、模板 = DSH Skill（Markdown） | 不写代码也能贡献；会长可以直接改 |
| **能力即工具** | 需要算/查/写/联动的 = DSH Tool（代码） | 复杂逻辑才写代码 |
| **入口即命令** | 高频动作 = 斜杠命令 | `/纳新 汇总` 比让 AI 猜要可靠 |

### 各域职责

| 插件 | 中文 | 管什么 | 典型命令 |
|---|---|---|---|
| `core` | 协会内核 | 身份、组织架构术语、成员名册读写、路径约定、事件总线 | `/计协` |
| `org` | 组织与成员 | 部门、成员、换届、权限、考勤 | `/成员 列表`、`/换届` |
| `recruit` | 纳新与迎新 | 报名收集、面试安排、录取、迎新包 | `/纳新 汇总` |
| `events` | 活动与项目 | 立项、审批流、场地、排期、复盘 | `/立项`、`/活动 复盘` |
| `finance` | 经费与物资 | 预算、报销、发票、物资台账 | `/报销`、`/物资` |
| `media` | 宣传与品牌 | 海报/推文规范、账号矩阵、舆情自查 | `/海报`、`/推文` |
| `report` | 报告与纪要 | 周报、月报、会议纪要、年审材料 | `/周报`、`/纪要` |
| `learning` | 竞赛与学习 | 集训、学习路线、竞赛报名、成果归档 | `/集训`、`/路线` |
| `kb` | 知识库 | 制度文件、SOP、模板、FAQ 检索 | `/查 报销流程` |
| `site` | 对外门户 | 官网/作品集/对外合作材料生成 | `/门户 构建` |
| `school` | 校务对接 | 社团管理系统、第二课堂等校方系统的对接台账 | `/校务` |
| `compliance` | 合规哨兵 | 红线自查（账号数量、舆情、整改期、名义使用） | `/自查` |

> `compliance` 单独存在的理由：社团最容易被「一票否决」的不是技术问题，是流程问题。把红线做成可执行的自查，比贴在群公告里有用。

## 五、单个插件包的标准形态

每个域插件都是一个**独立可发布**的 npm 包，内部结构统一：

```
packages/<domain>/
├── package.json          ← 含 "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
├── cordis.patch.yml      ← 声明本插件挂到 profile 树的位置与默认 config
├── README.md             ← 这个域管什么、怎么用、谁是归属人
├── OWNER.md              ← 归属人 + 交接须知（传承的关键）
├── skills/               ← 知识：制度、SOP、模板（Markdown，非程序员可改）
│   └── <skill-name>/SKILL.md
├── lib/
│   ├── index.js          ← 插件入口：name / inject / Config / apply
│   ├── tools.js          ← 需要计算/读写的工具
│   └── commands.js       ← 斜杠命令
└── data/                 ← 该域的初始数据模板（可被用户数据覆盖）
```

**归属人制度**：`OWNER.md` 里写清楚「这个插件谁负责」。换届时只要改这一个文件，责任就完成了转移。这是「一代一代传下去」在工程上的落点。

## 六、数据与知识的分层

```
distro 装的是「能力」（插件代码）
data/  存的是「事实」（协会真实数据）—— 独立于插件，可单独备份/归档
```

三级覆盖，从低到高：

1. **插件内置模板** — 出厂默认（如「报销单模板」）
2. **协会数据目录** — `~/.dsh/njau-ca/`（或仓库 `data/`）下的真实数据
3. **当届工作区** — 当前会话/项目里的临时文件

好处：升级插件不会覆盖协会真实数据；归档时只归档 `data/`。

## 七、传承机制（这是整个项目的真正目标）

技术会过时，**制度不会**。所以传承靠三样东西：

### 1. 归属人制度（`OWNER.md`）
每个插件有一个负责人。换届时签一次字，责任转移完成。

### 2. 决策留痕（`docs/adr/`）
「为什么用文件不用数据库」「为什么每个域一个插件」——写下来。
明年的人如果不同意，可以写一个新的 ADR 推翻旧的，而不是猜。

### 3. 年度归档（`docs/archive/<学年>/`）
```
docs/archive/2026-2027/
├── RETROSPECTIVE.md   ← 这一届做成了什么、没做成什么、为什么
├── plugins.json       ← 归档时刻的插件清单与版本号（可复现）
├── data-snapshot/     ← 协会数据的快照
└── handover-note.md   ← 给下一届的信
```

**换届 SOP**：
1. 跑 `node scripts/doctor.mjs` → 确认生态健康
2. 跑归档脚本 → 生成 `docs/archive/<学年>/`
3. 更新每个插件的 `OWNER.md`
4. 写 `handover-note.md`
5. `git tag` 一个学年版本，例如 `v2026-2027`
6. 下届 `git clone` + `node scripts/install.mjs` → 完整接手

## 八、分期落地

| 期 | 内容 | 判据 |
|---|---|---|
| **P0** | 内核 `core` + 发行版装配 + 安装/自检脚本 | `dsh` 起来后能看到计协身份、`/计协` 命令可用 |
| **P1** | `kb` + `report`（最通用、最快见效） | 能问制度、能出周报 |
| **P2** | `recruit` + `events` + `org`（事务主线） | 能跑完一次纳新 |
| **P3** | `finance` + `media`（容易踩线，要谨慎设计） | 能出报销单、能自查宣传红线 |
| **P4** | `learning` + `site` + `school` + `compliance` | 全生态 |
| **P5** | 传承文档、归档脚本、ADR | 换一届人能无损接手 |

## 九、明确不做的事

- ❌ 不做「又一个官网」——`site` 只是生态里的一个插件。
- ❌ 不把数据放进私有数据库——交接不了的东西不配存在。
- ❌ 不让业务插件互相 import——耦合是传承的敌人。
- ❌ 不在内核里写业务——内核一膨胀，整个生态就锁死了。
- ❌ 不把真实姓名、公司注册信息、内部汇报材料放进这个仓库。
