# 多人协作工作区 · 设计笔记

> 状态：**想法已记录，尚未落地。**
> 这是「要是能建一个多人协作工作区，像 work buddy 那样就好了」这个念头的存档。
> 记于 2026–2027 学年（第一届）。

---

## 为什么这件事对计协特别重要

协会的活儿**天生就是多人的**：会长定方向、部长带队、干事干活。
可现在每个人的 DSH 都是**自己机器上的一个本地应用**，数据也是本地的。

结果就是：**信息在三个人脑子里，不在一个地方。**
换届的时候最痛 —— 上一届的上下文没传下来，下一届从头猜。

`docs/vision.md` 里那条验收标准（「下一届的人能不能在不问你任何问题的情况下，
把一次纳新完整跑一遍」）本质上**就是一个协作问题**：不是缺工具，是缺一个共享的上下文。

## DSH 本身是什么、不是什么

**是什么**：一个本地优先的插件宿主。每个成员在自己电脑上跑一份 DSH，
装同一套 `njau` profile，就有同一套工具、技能、命令。

**不是什么**：DSH **没有多用户模型** ——
没有账号、没有权限、没有在线状态、没有实时同步。它也不知道「别人」的存在。

所以协作能力**必须由插件自己提供**。这不是缺陷，正是「一切皆插件」的意思：
DSH 给底座，协作层是我们的插件该干的事。

## 好消息：地基已经打好了

当初定下的铁律 3 —— **数据是纯文本（Markdown / JSON / YAML），永不引入数据库** ——
现在显出价值了：

| 因为数据是明文… | 所以… |
| --- | --- |
| 能进 git | 谁改了什么、什么时候改的，全有历史，能回滚 |
| 能 diff | 两个人的改动能合并，冲突是**可读的文本**，不是二进制锁 |
| 能被任何程序读 | 网站、脚本、别人写的插件都能直接用 |
| 不依赖某个软件 | 二十年后的学弟用一个文本编辑器就能看 |

**如果当初选了数据库，多人协作会难上十倍。** 现在它只是「把目录放哪儿」的问题。

## 三种做法（从省事到完整）

### 做法 A：共享数据目录 —— 零代码

把数据根指到大家都能访问的地方（学校服务器共享盘 / 网盘同步目录）。

- 怎么用：设置 `NJAU_CA_DATA` 环境变量，或在 `cordis.patch.yml` 里写 `dataDir`。
- 好处：**今天就能用**，一行配置。
- 代价：并发写会互相覆盖（两人同时改一个文件，后写的赢）；同步有延迟；权限粗。

**适合**：两三个人、以「看」为主的阶段。**这是最该先试的。**

### 做法 B：Git 工作区 —— 近零代码

协会数据目录本身就是一个 git 仓库。每人本地一份，改完 push。

- 好处：有完整历史、能回滚、能审阅、**天然就是"传下去"的载体**；
  冲突会明确告诉你「这两个人都改了同一段」。
- 代价：得有人懂一点 git；不适合放敏感材料（仓库可能被看到，见红线）。
- 好消息：`docs/archive/` 的年度归档规范**本来就是按这个设计的**。

**适合**：协会的**知识库、活动记录、章程、模板**这类「写一次、读很多次」的东西。

### 做法 C：插件化的协作中枢 —— work buddy 那种

这才是你想象的东西。做法是**一对插件**：

```
packages/hub/                     服务端（跑在学校服务器上）
  ├─ 宿主侧：ctx.webServer.register({ kind:'prefix', path:'/hub', handler })
  │          提供 HTTP API：任务、进度、谁负责、评论
  └─ 浏览器侧：一个协作面板，占 DSH 界面的 slot

packages/library/                 共享资源库（你点名过的）
  └─ 学习资料、模板、往届材料，也能挂在同一个服务器上
```

- 好处：真正的多人 —— 看板、认领任务、留评论、实时看到别人在干什么。
- 代价：**要一台服务器**；而且 DSH 不给账号和权限，
  这一层得我们自己写（**这是真正的成本，也是安全面**）。
- 注意：DSH 的 `webServer` 是给我们注册路由用的，
  但**认证、授权、防滥用全得自己来** —— 不能假装它是现成的。

**适合**：等做法 A/B 撑不住了再上。别一上来就做这个。

## 建议的走法

1. **现在**：做法 A。把数据根挪到一个共享位置，先让「信息在一个地方」这件事成立。
2. **下一步**：做法 B。数据目录 git 化，让改动有历史。这一步和「传下去」是同一件事。
3. **有服务器之后**：做法 C。先做 `library`（共享资源库，只读为主，风险低），
   再做 `hub`（可写、要权限，风险高）。

**顺序不能反。** 先有共享的**数据**，再有共享的**界面**。
反过来做（先做花哨的协作面板、数据还是各存各的）一定会烂尾。

## 红线

- **敏感材料绝不上共享层**：整改相关、关联方、内部汇报、个人隐私。
  共享目录里只放「全协会的人都该看到」的东西。
- **不做学校系统的自动登录/刷接口**（`GOVERNANCE.md` 第五节）。
  协作中枢是**我们自己的服务器**，不是学校系统的替身。
- 服务端一旦上线，**它就是对外服务**了：要有 HTTPS、要有访问控制，
  不能裸绑 `0.0.0.0` 就把协会数据摊在校园网上。
- 数据所有权不变：数据归**协会**，不归写服务器的那个人。

## 还没想清楚的

- 冲突怎么处理？「后写的赢」在台账类数据上会丢记录。
  （也许该像 git 一样：追加型数据永不冲突，修改型数据才需要合并。）
- 权限模型要多细？「会长能看全部、干事只看自己部门」——
  这需要一张权限表，而 DSH 不提供，得自己设计。
- 离线怎么办？成员在没网的地方改了数据，回来怎么合。
- 要不要有「谁在线」？这涉及隐私，可能不值得做。

## 一句话

**协作不是一个功能，是一个数据放哪儿的问题。**
我们选纯文本的那天，就已经把最难的一半解决掉了。
