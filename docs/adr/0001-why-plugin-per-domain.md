# ADR 0001 —— 每个业务域一个插件

- 状态：**已采纳**
- 日期：2026-10
- 决策者：2026–2027 届

## 背景

要给协会做一整套工具。可直接想到的做法是**做一个大插件**，里面分模块：
一个 `njau-ca` 包，`lib/recruit.js`、`lib/events.js`、`lib/finance.js`……

好处是简单：一个包、一次安装、共享代码方便。

## 决策

**每个业务域做成一个独立的包**，各自有 `package.json`、`cordis.patch.yml`、
`OWNER.md`，可以单独安装、单独删除、单独交给某个人。

## 理由

1. **换届时只需要交接一小块。** 下一届接手的人不需要理解整个系统，
   只要接手自己关心的那个域。这是一整个项目的核心目标 ——「传下去」。

2. **失败被隔离。** 某个域写坏了，删掉它，其余照常工作。
   一个大插件里某个模块抛错，可能整个插件都挂。

3. **责任可归属。** `OWNER.md` 挂在包上，"这个域谁负责"有明确答案。

4. **不需要共享代码。** 因为有了铁律 1（插件之间不互相调用）
   和铁律 2（零依赖），各域之间本来就没有多少可共享的东西 ——
   真正共享的只有「数据目录在哪」这个**约定**，它写在 `core` 的文档里就够了。

## 代价

- **包数量多**，每个都要写 `package.json` / `cordis.patch.yml` / `README.md` / `OWNER.md`。
  → 用一个脚手架脚本降低这个成本（待补：`scripts/new-plugin.ps1`）。

- **无法在代码层复用逻辑。** 两个域想共用一段逻辑时，只能各写一份。
  → 接受。这一段逻辑通常很短，而耦合的代价远大于重复的代价。

- **跨域操作要 agent 编排，不能一个函数调用搞定。**
  → 接受，而且这其实是好事：编排过程对用户是**可见**的（能看到 agent 调了
    哪几个工具），比一个黑盒函数更容易信任和排查。

## 被否决的替代方案

- **一个大插件**：违反"换届只交接一小块"，且失败不隔离。否决。
- **几个中等插件（按层分）**：层的边界会随需求漂移，会导致频繁重构。否决。
- **域插件依赖 core 提供的服务**：见 [ADR 0002](0002-plugins-do-not-call-each-other.md)，已推翻。
