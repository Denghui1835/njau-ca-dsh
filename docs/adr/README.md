# 架构决策记录（ADR）

> 「为什么当初这么做？」—— 答案在这里，不在某个人的记忆里。

---

## 为什么要有这个目录

换届时最贵的损失不是代码，是**当初为什么这么做**。

没有 ADR 的结果：

- 下一届看到 `priority: -1` 觉得莫名其妙，改成 `0`，然后界面崩了。
- 下一届觉得"数据应该上数据库"，花两周迁移，然后发现交接不了了。
- 下一届"好心"给所有包补上 `peerDependencies`，下次 DSH 升级后全部插件加载失败。

这三件事**都真实发生过或差点发生**。ADR 就是用来防这个的。

## 怎么写一份新的 ADR

文件名：`<四位序号>-<短横线连接的英文短名>.md`

内容至少包含这五节：

```markdown
# ADR 00XX —— <一句话决策>

- 状态：**提议中** / **已采纳** / **已被 ADR-YYYY 推翻**
- 日期：YYYY-MM
- 决策者：<哪一届>

## 背景
当时面对什么问题？为什么需要做决定？

## 决策
决定了什么？（要具体到能执行）

## 理由
为什么这么决定？

## 代价
**接受了什么坏处？** ← 这一节不许空着

## 被否决的替代方案
**想过哪些别的做法？为什么否决？** ← 这一节不许空着
```

---

## 两条硬规矩

### 1. 「代价」和「被否决的方案」不许空着

一份只说好处、不提代价的 ADR 等于没写。
下届看不到代价，就会以为可以随便改 —— 然后踩进你已经知道的坑里。

「被否决的方案」尤其重要：**不写下来，下届会把它们重新提一遍。**

### 2. 推翻旧决策要新写一份，不要删旧的

把旧的那份的状态改成「已被 ADR-XXXX 推翻」，然后在新的那份里
说明为什么要推翻。

**本仓库已经有先例**：ADR 0002 推翻了 v0.2 架构蓝图里
「域插件只依赖 `core`」的设计。旧设计仍然记录在案，
这样下届能看懂"为什么后来改成这样"，而不是以为一开始就对了。

---

## 什么时候该写 ADR

- 做了一旦定下就很难改的决定。
- 推翻了已有的决定。
- **否决**了一个看起来很有道理、以后还会被重新提出的方案。
  （这一条最容易被忽略，但价值最高。）

什么时候不用写：改个文案、调个参数、修个 bug —— 这些写进 `CHANGELOG.md` 就够。
