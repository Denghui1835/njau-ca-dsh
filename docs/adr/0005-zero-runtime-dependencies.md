# ADR 0005 —— 零运行时依赖，且不声明任何 `@deepseek-ai/*` peer

- 状态：**已采纳**
- 日期：2026-10
- 决策者：2026–2027 届

## 背景

写一个 DSH 插件，自然会想：

- 用 `@deepseek-ai/dsh-*` 里的工具函数，省得自己写；
- 在 `package.json` 里声明 `peerDependencies: { "@deepseek-ai/dsh": "^0.2.0" }`，
  "表明我依赖哪个版本"，看起来是好习惯。

## 问题

DSH 启动时会做一次插件兼容性检查（`evaluatePluginCompatibility`）。
实测其行为：

> **它只检查你在 `package.json` 里声明过的 `@deepseek-ai/dsh*` peer 依赖，
> 比对版本时 `includePrerelease: true`。没声明的，完全不检查。**

于是产生一个反直觉的结论：

**声明 peer 依赖不会让你更安全，只会让你更容易被拒载。**

因为：

1. DSH 目前是 `0.2.0-rc.2` 这种**预发布版本**，版本号变化频繁。
2. 一旦声明的范围没覆盖到新版，插件就**加载失败** —— 哪怕代码其实完全能跑。
3. 我们的插件实际只用最稳定的那部分接口（注册工具、技能、命令、提示词段），
   这些接口极少变。真正会变的是客户端内部结构（见 ADR 0004），
   而那个**不受 peer 检查保护**。

## 决策

**两条一起：**

1. **不 `import` 任何 `@deepseek-ai/*` 运行时包。** 只用 Node 内置模块
   （`node:fs`、`node:path`、`node:os`、`node:url`）。

2. **不声明任何 `@deepseek-ai/*` peer 依赖。** `package.json` 里
   连 `dependencies` 都是空的。

唯一的例外是**浏览器侧**代码可以 `require('react')` 之类 ——
那是 DSH 提供的静态模块表，不是 npm 依赖，不需要声明。

## 理由

1. **声明得越少，越不容易被 DSH 升级拒载。** 一个都不声明最安全。

2. **零依赖 = 零供应链风险。** 插件的代码量是几百行，
   审一遍很快；有依赖就没底了。

3. **零依赖 = 装得上。** 不需要联网装包，不会因为 registry 挂了而装不上。

4. **被迫自己写的那点代码其实很少。** 实测写下来，需要自己实现的只有：
   路径安全校验、原子写文件、读 JSON、列目录 —— 加起来不到 100 行。
   为这点代码引入依赖不划算。

## 代价

- **要自己写样板。** 路径校验、原子写、容错读 JSON 都得自己实现。
  → 接受，而且这些代码**一次写对就再也不用动**（它们是纯函数，无外部状态）。

- **拿不到 DSH 内部的便利工具。** 有些明显的工具函数得自己写一遍。
  → 接受。也避免了对内部实现的依赖 —— 那些工具可能哪天就改名了。

- **每个插件各写一份。** 因为铁律 1 不允许共享库（那也是个依赖）。
  → 接受。这十几行代码的重复是可接受的代价。

## 一个反直觉但重要的推论

**"声明依赖"在很多生态里是良好实践，在这里是负资产。**

这条结论不是推测，是读 DSH 的兼容性检查代码 + 实测装包后得出的。
如果不写下这份 ADR，下一届很可能"好心"地给所有包补上 peer 依赖声明，
然后在下一次 DSH 升级后**全部插件一起加载失败**，而且不知道为什么。

这就是这份 ADR 存在的意义。
