# ADR 0002 —— 插件之间不互相调用，core 不提供任何服务

- 状态：**已采纳（推翻了 v0.2 的设计）**
- 日期：2026-10
- 决策者：2026–2027 届

## 背景

v0.2 的架构蓝图写的是：

> 「插件之间不直连：域插件只依赖 `core`，彼此通过 core 的数据层或事件通信。」

也就是说：`core` 对外提供一个 Cordis 服务（比如 `ctx.njau`），
里面放共享的数据读写、事件总线；各域插件 `inject: ['njau']` 来用它。

这在设计阶段看起来是标准的插件化写法 —— 有一个共享内核，大家依赖它。

## 问题

实施时发现：**只要 `core` 对外提供服务，`core` 就变成了所有插件的公共依赖。**

于是：

- `core` 的任何接口变动都会**同时**影响所有域插件 → 违背「内核极薄」。
- `core` 里加一个方便的方法，就会有插件开始依赖它 → 内核**持续膨胀**。
- 想删掉一个域插件时，要先确认 `core` 里有没有只为它加的东西 → 「可拆卸」失效。
- 最要命的：**`core` 一改，全生态一起坏** —— 正好是我们要避免的局面。

## 决策

**插件之间不互相调用，`core` 也不对外提供任何 Cordis 服务。**

`core` 退化为**一个约定**，而不是一个**接口**：

- 数据目录在哪（`~/.dsh/njau-ca`，可被 `NJAU_CA_DATA` 或 `dataDir` 覆盖）
- 目录怎么组织（按域、按学年）
- 命令怎么命名（`njau-*`）
- 路径安全怎么做（`resolveInside`）

每个域插件**自己**读环境变量、**自己**拼路径、**自己**读写文件。
它复制了十几行样板代码，换来的是**彻底的独立**。

**跨域协作由人（和 agent）编排多个插件的工具完成**，不发生在代码层。

例：把纳新结果汇总进周报 ——
agent 先调 `recruit` 的工具读报名数据，再调 `report` 的工具写周报。

## 理由

1. **约定可以变，接口不能轻易变。** 约定变了，各域各自改一行；
   接口变了，所有依赖方都得改。

2. **可拆卸成为事实，而不只是口号。** 删掉任何一个域插件，
   不需要动 `core`，也不需要考虑别人。

3. **编排过程可见。** 用户能看到 agent 调了哪几个工具，
   比藏在一次函数调用里更容易信任和排查。

4. **复制十几行比引入一个依赖便宜。** 尤其在"要传十年"的语境下。

## 代价

- **样板代码重复。** 每个域都要自己解析数据根、自己做路径校验。
  → 缓解：把这十几行写成一个**可以整段复制**的模板，放在
    `packages/core/README.md` 里（待补），而不是做成一个共享库。

- **没有任何编译期/加载期的跨域一致性检查。**
  → 接受。跨域一致性本来就不该由代码保证，而该由**流程**保证。
