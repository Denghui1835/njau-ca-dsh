# ADR 0003 —— 数据放文件，不放数据库

- 状态：**已采纳**
- 日期：2026-10
- 决策者：2026–2027 届

## 背景

协会的业务数据有：成员名册、活动记录、经费台账、物资清单、
报名信息、会议纪要、周报月报。

规模估算：**成员几百人、活动每年几十场、经费每年几十笔。**
这是极小规模的数据 —— 小到用 Excel 都能管。

但"数据该放哪"是一个必须现在就定的问题，因为它决定了**十年后这些数据还在不在**。

## 决策

**一律用 Markdown / YAML / JSON 纯文本文件**，按域和学年组织在数据目录里。
**永不引入数据库**（SQLite 也不行）。

## 理由

1. **数据是资产，代码是耗材。** 代码会被下一代重写，数据不会。
   所以数据格式必须比代码活得久。纯文本活得过任何框架。

2. **能被十年后的人用记事本打开。** 这一条压倒一切。
   十年后不会有人为了看 2026 年的活动记录去装一个特定版本的数据库驱动。

3. **能进 git。** 于是自动获得：diff、blame、回滚、code review、分支实验。
   数据库的二进制文件在 git 里是灾难。

4. **能人工修。** 数据错了，用记事本改一行就好 —— 不需要写 SQL，
   不需要求会 SQL 的人。

5. **交接就是打包。** 把数据目录压缩发给下一届，结束。
   不需要"数据导出"这种一次性消耗品，也不需要迁移脚本。

6. **数据量根本不需要数据库。** 几百条记录用 `grep` 就够快了。
   上数据库是纯粹的过度工程。

## 具体格式约定

| 用途 | 格式 | 理由 |
| --- | --- | --- |
| 台账、清单、记录（多条同类） | **JSON 数组** | 机器读写，结构化 |
| 文档、纪要、周报、总结 | **Markdown** | 人要读，要能直接贴进群里 |
| 配置、模板、索引 | **YAML** | 人写起来舒服，能写注释 |

**写入一律原子**：先写临时文件再 `rename` —— 避免断电/崩溃留下半个文件。
`core/lib/store.js` 的 `writeTextFile` 已经这么做了。

## 代价

- **并发写没有保护。** 两个人同时改同一个文件会互相覆盖。
  → 接受。协会场景里"同时改同一个文件"几乎不会发生；
    真发生了，git 会告诉他。数据库解决的是一个不存在的问题。

- **查询要全量读。** 想查"去年参加过活动的所有人"，得遍历所有活动文件。
  → 接受。数据量小到无所谓；真慢了再建索引文件（**索引也是文本**）。

- **没有 schema 强制。** 写错字段名不会被发现。
  → 缓解：由域插件的工具负责写入（工具内部校验），
    而不是让人直接编辑文件。但**允许**人直接编辑 —— 这是特性不是缺陷。

## 被否决的替代方案

- **SQLite**：跨机器拷贝仍然方便，但失去了 diff/blame/人工修，
  而且十年后要确认驱动仍在。收益不抵损失。否决。
- **JSON + 一个查询库**：引入了依赖（违反铁律 2）。否决。
- **云文档/在线表格**：数据不在协会自己手里，且换届时拿不回来。
  这正是当前痛点（纳新在问卷星、活动在腾讯文档）。否决。
